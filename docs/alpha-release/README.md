# TrainerOS — досье альфа-релиза

**Рабочая папка подготовки выпуска. Не является объявлением о готовом публичном релизе.**

Начато: 2026-11-03. Исходная точка ревизии: `main` @ `2a6c9c9b00b58e914525bd779c76896c8fcf5006`.
При каждом значимом изменении проверять свежий HEAD и уточнять, к какой сборке относятся доказательства.
Название «альфа» — рабочее обозначение предстоящей публикации; версии/каналы дистрибутива определяются отдельно.

## Назначение

Составить **полную, проверяемую опись того, что умеет TrainerOS именно сейчас**:
- функции, экраны, действия и пользовательские сценарии;
- установка, поддерживаемые устройства и системные требования;
- реально проверенные игры, платформы, адаптеры и виды мультиплеера;
- ограничения, известные поломки, зависимости и ещё не пройденные проверки;
- отдельные человеческие описания блоков;
- после аудита — готовые тексты для сайта, GitHub, Discord, Reddit и иных площадок.

**Не смешивать четыре вещи:** намерение/контракт, код в ветке, фактически установленную сборку и успешный пользовательский тест.

## Словарь доказательств

- `TARGET` — утверждённая задумка, **не** работающий функционал.
- `CODE` — найден в исходниках **конкретной ветки/ревизии**.
- `INSTALLED` — присутствует на названном устройстве/в конкретной сборке.
- `TESTED` — успешный воспроизводимый тест с указанными условиями.
- `PARTIAL` — реализовано/проверено лишь частично; обязательны ограничения.
- `OPEN` — недостаточно данных или ещё не проведена проверка.
- `BLOCKED` — известный стоп-фактор; указывать симптом и ссылку.
- `N/A` — не применимо, с объяснением.

В матрицах `?` означает «**ещё не проаудировано для этого досье**», а не «функция отсутствует».
Для описания одной функции можно иметь сразу несколько статусов: например, `CODE` и `OPEN` по физической проверке. Нельзя автоматически повышать `CODE` до `TESTED` или `TARGET` до `CODE`.

## Порядок работы

1. Зафиксировать **срез**: ветка/коммит, модель устройства, сборка, дата.
2. Постепенно заполнять матрицу: пользовательский путь → код → тест → ограничения → ссылки.
3. Проверить отдельные рабочие ветки и отметить то, чего пока нет в `main`.
4. Написать по одному самостоятельному файлу на каждый блок системы.
5. Проверить запуск, установки/обновления и совместимость; отделить блокеры выпуска от недоделок.
6. Из подтверждённого материала собрать описание системы, FAQ, список возможностей, объявления и посты. **Не обещать неподтверждённое.**

Это живое досье с версионируемыми фактами, а не второе хранилище технических логов.
