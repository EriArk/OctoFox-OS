## Проход на Flip

Перед установкой исходная сессия была Armada/Steam, без установленного
TrainerOS launcher. Сохранялись неполные остатки старого beta/preview Setup.
Неактивный root без receipt/journal/owned files отложен отдельно; его trust и
bootstrap не переименованы в Alpha. Все сохранённые личные profile/runtime homes
и последний pre-clean recovery root оставлены.

Очищены только неактивные распакованные runtime generations двух старых
удалённых установок, staging прерванной установки и generated object/resource
каталоги старой сборки. Проверены отсутствие active/previous receipts, pending
journals и live references. Runtime manifests и code recovery blobs сохранены;
игры, BIOS, saves и runtime-home не входят в удаление.

Новый Setup скачан через HTTPS на microSD, размер и SHA-256 проверены, архив
распакован. Обычный `Install TrainerOS.sh` запущен **один раз** из Desktop при
отсутствующих program/profile roots. Через реальные kdialog окна выбран Alpha
и подтверждена установка. [Подтверждение](setup-confirm.png),
[проверка комплекта](setup-progress.png). Ввод передан виртуальной USB-клавиатурой
через uinput; это удалённая проверка UI, не доказательство физических кнопок.

Последний полученный этап — подготовка `org.kde.Platform/aarch64/6.10`.
Затем Flip продолжал отвечать на ping, но новые SSH-команды перестали
возвращать результат. Это не доказательство завершения или падения Setup;
принудительно прерывать работающий установщик не стали. Владелец подтвердил
живое окно и растущий таймер; на фото — подготовка KDE 6.10, 9m17s. Это
подтверждает работу окна, но не продвижение дочернего процесса упаковки.
Финал Setup, новый wizard, восстановленные аккаунты,
импорт/запуск, Apps/Quick Apps и реальный OTA пока не засчитаны.

гарантия отображения при зависании всей ОС или гибели всей графической сессии.

также проверены: исходное окно остаётся при отказе нового диалога, подтверждение

`a0585985-f5dc-4f01-9884-2a28a8f699d8`; SSH снова выполняет команды.

### Проверки на Flip и блокировка записи

На настоящем Flip отдельно от работающего Setup проверены два сценария:
[обычная ошибка](flip-error-test.png) остаётся видимой (повторный кадр через 10 с
совпал), OK закрывает её и возвращает исходный прогресс установки; аварийный
выход отдельного тестового worker с кодом 7 вызывает
[сообщение supervisor](flip-supervisor-test.png), сохраняет диагностику в журнале
с режимом 0600 и закрывается по OK. Сообщения явно отмечены TEST ONLY;
настоящая установка этими тестами не прерывалась.

Повторный Setup прошёл обе подготовки KDE 6.10/6.11, но при скачивании RetroArch
внутренняя запись заблокировалась. Last phase — download RetroArch (4m53s),
Software/runtime receipts и activation journal ещё отсутствовали. IO PSI some
достиг 96%, full — 87%; memory PSI оставался 0. [Снятые kernel stacks](flip-ufs-stall.txt):
`ostree` ждёт Btrfs metadata reservation, writeback — block request tag,
UFS exception worker — `blk_execute_rq` из `ufshcd_exec_dev_cmd`, devfreq worker —
`ufshcd_devfreq_scale`. Сам Setup также попал в ожидание записи журнала.
Это блокировка хранения ниже установщика, а не доказательство нехватки RAM.

Сигнатура соответствует [описанному UFS clock-scaling deadlock](https://lkml.iu.edu/2610.2/01240.html).
Проверен исходник Armada `066ecdc`: base kernel 7.2.6, в patch set нет перестановки
этих блокировок. В [Linux 7.2.6](https://raw.githubusercontent.com/gregkh/linux/v7.2.6/drivers/ufs/core/ufshcd.c)
очередь останавливается до взятия clk_scaling_lock, как в описании ошибки.
Это обоснованный диагноз по стеку и исходникам; исправленное ядро на Flip не тестировалось.

Владельцу запрошена перезагрузка. Подготовлена проверка с временным отключением
UFS clock scaling через документированный `clkscale_enable=0` после нового boot;
запись этого параметра в уже заблокированном состоянии не выполнялась.
Перепаковка KDE в локальный Flatpak bundle остаётся отдельным лишним расходом
времени, её устранение этим изменением не реализовано. Автоматический вход
после установки и device OTA до разблокировки устройства **не засчитаны**.

## Устранение лишней подготовки и проверка старого ядра

После следующей перезагрузки владельцем Flip загрузился с boot ID
`06af7395-e0c9-4e45-8cf5-93d9043ae616`. При низком IO pressure временно,
только для этой загрузки, установлен `clkscale_enable=0` у `1d84000.ufshc`.
Прочитанное значение — 0. Постоянного правила или исправленного UFS-ядра пока нет.

Уточнение к словам «Iris сохранён» выше: сохранена **закреплённая загрузка для
отката**, не действующий фикс. В старом журнале Flip подтверждено реально
загруженное `7.2.6-traineros-iris1`; сейчас загружены Armada 20261110.066ecdc и
обычное `7.2.6`, `/usr/lib/modules` содержит только его. Iris deployment и boot
entry остаются закреплёнными. Odin также подтвердил обычное `7.2.6`, Armada
20261110.066ecdc и закреплённый Iris fallback. Точный апдейт, первым заменивший
активное ядро Iris, этим чтением не установлен. В исходниках этой Armada и base Linux 7.2.6 не
найдены наши request-keyframe и gen1-visible-input-size изменения. Это регрессия
проверенного видеопотока после перехода на vanilla Armada; сохранённый rollback
не означает сохранение функции в активном ядре. Она не объясняет UFS stack:
старые патчи относятся к Iris encoder, а не накопителю. Возвращение этих патчей
на актуальную базу и повторная проверка видеопотока остаются открытыми.

В подготовке Setup удалены следующие затраты:

- Скачанные и проверенные Flathub commits больше не перепаковываются в локальные
  `.flatpak`. Малый descriptor удерживает exact commit, исходный repo и hash ключа.
  При активации `ostree pull-local --untrusted --gpg-verify` проверяет подпись и
  объекты; `flatpak install --no-pull` развёртывает закреплённый ref без сети.
  Исходный cache удерживается для отката. Старые bundle journals и изменённый
  PPSSPP продолжают работать; recovery export нужен лишь для прежнего неуправляемого ref.
- После потоковой проверки распаковки больше нет немедленного второго чтения
  всего media. Проверка подписанного staging перед планированием остаётся.
  Проверенный component не сканируется второй раз после atomic rename; Python
  environment inventory вычисляется один раз за неизменившееся состояние.
- Согласие обновить системный helper продолжает подготовленный план вместо
  повторного скачивания/проверки всех эмуляторов и окружений.
- Code/recovery copies используют Linux reflink с обычным копированием при
  неподдерживаемой файловой системе. Это независимые inode, не hard links.
  Проверки hashes, fsync и защиты изменённых пользователем файлов сохранены.
  Исправлена также проверка уже существующего recovery blob при импорте.

Проверены 38 Software Installation, 7 Setup UI, 27 Runtime Installation,
5 Flathub, 3 Environment Recovery, 8 Payload и 16 Upstream tests.
Дополнительно настоящие Flatpak/OSTree/GPG в контейнере **без сети** прошли три
сценария: runtime+app install/update/interruption/rollback/remove с сохранением
save; переход со старого bundle и обратный recovery; отказ для неподписанного
commit и повреждённых объектов. Изменённый staging ref не подменяет exact commit.

Исправления прочитаны обратно по hash на Flip; запущен обычный GUI Setup с
обновлением bootstrap, выбором Alpha и подтверждением Install. Старые подписанные
