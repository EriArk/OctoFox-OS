# OctoFox OS — непрерывные доверенные сейвы и рыночный лут

> **Статус:** живая спецификация будущего **экономического доверенного режима**, решения владельца от 22 ноября 2026. **Не утверждает**, что Verified Session, экспорт в server custody и защита от произвольного пользователя с root уже реализованы. Изменения в обычном режиме игры не требуются.
>
> См. [живую экономическую спецификацию](ECONOMY_LIVING_SPEC_RU.md), [имеющийся Save Lineage](SAVE_LINEAGE.md), [#93](https://github.com/EriArk/OctoFox-OS/issues/93), [#94](https://github.com/EriArk/OctoFox-OS/issues/94), [инвентарь](PROFILE_INVENTORY.md).

## 1. Зачем нужна эта граница

Будущий общий Bazaar должен принимать редкие и ценные предметы **из обычных игр через адаптеры**. Нельзя допускать, чтобы один редкий дроп многократно попадал в обращение благодаря импорту старых сейвов, savestate, свободным веткам или повторным запросам.

**Принцип владельца: для доверенной рыночной истории — одна игра → один сейв → одна непрерывная линия. Импортированные, повторные и дублированные ветки неприемлемы для создания торгуемого лута.**

Ожидаемая пользовательская база может быть небольшой (в обсуждении предполагалось до ~600); это не повод проектировать абсолютную защиту от root любой ценой, но двойная выдача товара и нарушение серверного владения неприемлемы на любом масштабе.

## 2. Жёсткие правила доверенной истории [ПРИНЯТО]

- Для каждого OctoFox-аккаунта и точной игровой идентичности — **одна активная доверенная линия и один актуальный доверенный слот сохранения** для выхода на рынок. Политику нескольких разных изданий/версий игры определить отдельно.
- **Новый доверенный путь начинается с новой игры**, а не из загруженного извне сейва. Импортированный файл, его клон и старое внешнее состояние не могут стать источником подтверждённого рыночного лута.
- **Никаких пользовательских параллельных веток, savestate, rewind или возврата к более раннему сейву** внутри этого режима. Старые файлы не предлагаются как игровые слоты для последующей торговли.
- Каждая новая доверенная ревизия обязана продолжать последнюю принятую ревизию и проходить необходимые проверки игры, адаптера, save ownership и среды исполнения.
- На втором устройстве нельзя независимо запустить вторую активную ветку того же доверенного сейва. Перенос требует остановки/завершения предыдущей сессии и монотонного handoff.
- Доверенные предметы можно выводить из игры в общий инвентарь **только из последнего допустимого состояния**.
- Настройка действует на **экономический trusted-режим**; обычные локальные игры, неэкономические сейвы, импорт, моды, свободные эмуляторы и savestate остаются разрешёнными, просто не получают права на подтверждённую рыночную эмиссию лута.
- Уход из trusted-режима не удаляет пользовательские файлы. Возвращение из недоверенной ветки в рыночную историю не допускается простым «проверить ещё раз» или переименовать файл.

**Открытый продуктовый вопрос:** допускается ли вообще аварийное служебное восстановление, и если да, как оно выглядит без возвращения к прошлой торгуемой ревизии. Технические recovery-копии для аварийного ремонта не должны становиться вторым играбельным слотом; всегда требуется проверка неотзывных операций и последнего серверного checkpoint.

## 3. Проверяемая сессия, а не один только хеш

Подпись сохранения сама по себе не доказывает честный лут. Программа или пользователь могут изменить память эмулятора, после чего игра сама запишет синтаксически правильное сохранение.

Для подтверждённого режима адаптер и платформа могут потребовать:
- точный хеш ROM/игры и поддерживаемую версию;
- зафиксированный эмулятор/core/runtime и допустимые настройки;
- отдельное контролируемое пространство сохранений;
- отсутствие запрещённых читов, сторонних memory writers, rewind/savestate — в объёме, который платформа реально способна наблюдать;
- привязку игрового запуска/завершения, активного аккаунта, ревизии сохранения и цепочки изменений;
- внешние, **серверно закреплённые монотонные checkpoints**, чтобы старый локальный signed prefix нельзя было выдать за последнюю ветку;
- отдельно — семантическую проверку адаптером конкретного предмета и игрового прогресса.

**Текущий факт:** `docs/SAVE_LINEAGE.md` документирует локальную подписанную Ed25519-цепочку `imported`/`managed`, но **без verified-гарантии** и без неподделываемого аппаратного корня доверия. Ключи программные; root/полный контроль над хостом потенциально позволяют копировать ключи и подменять исполняемую среду. Подтверждение аномалий и серверный checkpoint — будущие контракты, не уже имеющиеся средства абсолютной защиты.

## 4. Сохранение → серверный предмет → Bazaar → возвращение в игру

Ожидаемая цепочка:
1. Проверить последнюю допустимую server revision, принадлежность аккаунту, точную игру/адаптер и право на экономический экспорт.
2. Адаптер определяет **конкретный** экземпляр (вместе с игровыми характеристиками/метаданными) и проверяет допустимость вывода. Дубликат внутриигровой сущности не превращать в новый объект только сменой UI-идентификатора.
3. Под защитой менеджера сохранений подготовить удаление/вывод экземпляра из **единственного актуального** сейва; сохранить идемпотентный operation ID и recovery-состояние.
4. Подтвердить защищённую запись, повторное чтение результата и отсутствие экземпляра в активном сейве. Только потом финализировать **единственное** серверное владение экземпляром.
5. В server inventory предмет имеет уникальный ID, исходную игру/адаптер, оригинальные параметры и непрерывную цепочку custody. Он не принадлежит одновременно активному сейву и торгуемому профилю.
6. Bazaar листинг блокирует предмет до продажи/снятия. Покупка атомарно меняет серверного владельца, переносит Искры, сжигает комиссии и пишет единственную квитанцию.
7. Возвращение предмета требует подходящей версии игры/адаптера, доступной ёмкости и защищённого импорта в последнюю доверенную ревизию покупателя. Предмет снимается с серверного свободного владения только при подтверждённом результате, с idempotent recovery.

**Сбой между файлами и сервером:** локальную запись и SQL-коммит нельзя выдавать за одну распределённую атомарную транзакцию. Нужен durable pending-протокол, при котором повтор/перезапуск возобновляют **ту же** операцию, не создавая вторую сущность. До полного разрешения нельзя показывать предмет одновременно доступным к продаже и доступным в игре. Решение о компенсации/восстановлении определять по последнему подтверждённому состоянию, а не по ответу игры/сети «кажется, успех».

**Не считать решённым:** offline copy и пользователь с root могут пытаться подделывать клиент, ROM, память или откатить локальное хранилище. Сервер не должен принимать старую ветку как новую только за наличие локально валидной подписи. Для более строгой защиты в будущем возможны аппаратная аттестация или контролируемое исполнение, но вводить их без исследования поддержки устройств не нужно.

## 5. Вклад адаптера

- Адаптер владеет структурой сейва, поддерживаемыми точными билдами, специфичными правилами предмета, семантической проверкой и преобразованием protected candidate.
- Общая платформа владеет доступом к файлам, подлинным активным Trainer, backup, блокировками, атомарной записью/readback, server checkpoint и межустройственным handoff.
- Backend владеет одинарным server custody, историей передачи, торговыми правами, Искрами и квитанциями.
- Нельзя «выписывать» невиданные предметы в мир только по заявлению клиента; требуются подтверждённая игровая сущность и поддерживаемая сессия.
- Редкость/шансы выпадения приходят из **оригинальной игры**; OctoFox не повышает шанс и не присваивает предмету фиктивный «легендарный» статус. Для предметов с вариантами свойств сохраняется точная идентичность экземпляра.
- Первой целевой вертикалью остаётся точный **Pokémon Emerald**; затем — игры с редким лутом, которые реально позволяют безопасно идентифицировать, извлечь и вернуть экземпляр. Не обещать универсальную поддержку произвольной игры.

## 6. Категории состояния (предложение терминов)

| Состояние | Игра доступна | Может создавать новый рыночный лут |
| --- | --- | --- |
| Обычное/импортированное/неизвестное | Да | Нет |
| Локально управляемое, но без полного подтверждения | Да | Нет |
| Доверенное (единая серверно закреплённая линия + проверяемая сессия) | Да | Да, только у поддерживаемого адаптера |
| Нарушенная/откаченная история | Да, в свободном режиме | Нет |

Это **граница экономических прав**, не наказание, бан или автоматическое обвинение в читерстве.

## 7. Проверки для первого сквозного сценария

- Создать новую trusted-игру Emerald; сохранить последовательные ревизии; извлечь отдельную разрешённую сущность; убедиться, что обычная Emerald больше её не видит.
- Подтвердить одну server custody-запись; после продажи/вывода/возврата сверить точные save-изменения и одно владение.
- Повторный export с тем же и с новым operation ID; гонка запросов; откат к прошлой копии; попытка импортировать внешний save; попытка открыть второй trust-slot — **не должны создавать новый товар**.
- Сбой до/после удаления из сейва, до/после server custody, потерянный HTTP-ответ, перезапуск игры/оболочки, переход на другое устройство, несовместимый import — без удвоения, потери подтверждённого предмета или неверных чеков.
- Проверить непротиворечивые статусы без выдуманной аппаратной гарантии. Обычные сейвы, импорт и офлайн-игры не должны становиться недоступными.
- Не смешивать уже работающий **Emerald Link** (локальный защищённый обмен с собственной игровой валютой) с новым **Bazaar server custody**: это разные цепочки приёмки.

## 8. Состояние реализации и следующие вопросы

**Уже есть:** локальная подписанная история и protected save edit для поддерживаемых путей; точные Emerald-семантические операции/Link; серверный private inventory read, а для собственных Ship Home-товаров — мастерская и торговые операции.

**Ещё не реализовано/не принято как полный сквозной механизм:** universal Verified Session; серверные monotonic checkpoint; единая trusted-линия на несколько устройств; защищённое удаление Emerald-сущности в server inventory; возврат из server custody; публичная торговля адаптерными предметами. Production Bazaar spending сейчас отключён.

**Открыто:** определение игровой идентичности и запрет нескольких копий разных ROM-редакций; стратегия после краша и невозможности восстановить текущий сейв; защита от форков при офлайне и межустройственном переходе; сколько и каких событий нужно проверять против клонирования rare drops; насколько аппаратный корень доверия реально доступен на Armada/Odin/Steam Deck/Linux; допустимы ли неторговые предметы/подарки внутри доверенного мира (без прямого перевода Искр).

## 9. Журнал решений

- **2026-11-22:** для торговли введена продуктовая цель «один новый trusted-сейв, одна непрерывная история, ни импортов, ни дублей, ни пользовательских откатов»; граница относится к экономически доверенным предметам, не к обычному свободному одиночному режиму. Начать с Pokémon Emerald и расширять на игры с редкими предметами по мере появления адаптеров.
