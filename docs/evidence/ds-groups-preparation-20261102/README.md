# DS Wireless 2–4 и ARM64 WFC — подготовка без портативок

2 ноября 2026. R043 / S03, S06, S08. Основа — `a145f7b0`: сохранены изменения
Home, уведомлений и Wi-Fi другого потока. Flip/Odin не подключались и не
обновлялись. Сборка и ARM64-прогоны выполнены на сервере; локально — C++ проверки
оболочки. Это подготовка поставки, не новая игровая или аппаратная приёмка.

## Изменение поведения

Новый пакет `detmp-group-owned-v2` открывает 2–4 места в обычном DS Wireless
Lobby. Пакет `detmp-two-owned-v1` по-прежнему объявляет два места. Идентичность
включает точную сборку, settings и содержимое картриджа. Ограничения по списку
проверенных названий нет; сохраняются NDS/SRL и однозначные ZIP/7z.

После явного Start каждый участник получает свой экран и ввод. Для трёх/четырёх
участников хост создаёт отдельный существующий secure-channel для каждого гостя:
Nearby TLS либо Online Magic Wormhole/Dilation. Приватный endpoint отправляется
только назначенному месту через `GameParty::readyMember`. Состав и номер места
перепроверяются перед запуском. Вход в комнату сам по себе игру не запускает.

Новый `GroupRemoteSession` координирует существующий NativeSession/DetMP:
обмен собственными opaque seeds, общий input delay, ограниченные очереди,
проверка состояния каждой DS между всеми участниками и согласованная граница
выхода. Чужие копии остаются временными; возвращается только собственный сейв
через прежнюю защиту `RuntimeSaveStorage`. Обрыв или несовпадение до подтверждённого
возврата запрещают commit. Потеря связи не подменяется автоматическим запуском.

При ARM64-прогоне исправлена гонка окончания: быстрый клиент уже сохранил
подтверждённый результат и закрыл helper, а медленный хост ещё обрабатывал EOF.
Закрытие принимается штатно только после retained-квитанций **всех** владельцев.
Ранние разрывы остаются ошибкой. Проверка `early-close` отдельно покрывает этот
случай реальным закрытием процесса, а отрицательные loss/mismatch остаются красным
путём без разрешения возврата.

## Проверки

- Серверный Linux x86_64: 11 сценариев координатора через реальные TLS helpers:
  3/4 участника, обычный/ранний штатный выход, отказ admission, рассинхронизация,
  потеря участника и новая комната после потери. Различные синтетические seeds
  проверяются у каждого получателя; один владелец начинает с fresh.
- Полный Qt/SDL frontend с настоящим melonDS: независимые процессы для 2, 3 и 4
  участников, то есть 4/9/16 DS суммарно. Свободный минимальный картридж,
  контрольные состояния и согласованный выход. Исходный картридж не изменён,
  у каждого процесса только собственная корректная no-save квитанция.
- Тот же путь на ARM64 под QEMU, включая ARM64 Python 3.14.8, TLS/crypto
  зависимости и настоящий ARM64 frontend: 2/3/4 участника прошли; конечные
  границы 106/107/108 кадров. Это не замер производительности портативок.
- ARM64 WFC: два отдельных запуска ядра, 600 кадров; FreeBIOS/firmware,
  SLIRP init, AP/DNS/CRC, стабильный MAC, повторное чтение собственного
  синтетического WFC ID, неизменность картриджа. Сервисный матч не запускался.
- Qt 6.11.1 / Windows: RuntimeMultiplayer **108/0**, protected saves **33/0**;
  проверка сохранений теперь проходит все места в составах 2/3/4 и семь исходов.
  Адресные DS endpoints: **3/0**, включая init/cleanup. PreparedSession проверяет
  все owner slots в группах и отклоняет выдуманный fresh вместо peer state.
- Общий standalone: **82 passed / 2 failed / 11 skipped**. Две прежние ошибки
  Unix-permissions NativeLan на Windows остаются из [предыдущего прохода](../ds-wfc-20261102/README.md);
  проверки и защитные условия не ослаблялись. Дополнительный skip — Linux-only
  строка нового группового пакета. Отдельный endpoint-тест выполнен после этого run.
- Linux admission probe против настоящих `MelonDsNetplay.cpp`/`CartridgeContent.cpp`:
  старый пакет даёт 2 места, новый 4; произвольный SRL допускается, неизвестная
  settings-версия отвергается. Это отдельно закрывает изменённую границу,
  пропущенную Windows-only окружением полного standalone suite.

Первый native frontend-прогон упал с SIGBUS в `Savestate::VarArray`: Docker
предоставлял только 64 MiB `/dev/shm`. Отдельный контейнер с `--shm-size=1g`
устранил нехватку для нескольких процессов. Это ограничение стенда, не исправление
сетевого протокола. Память и CPU растут с числом зеркальных DS; число мест не
является обещанием скорости на каждой портативке.

Внутренний SHA256SUMS Wireless проверен до архивирования; ARM64 PreparedSession
проверка также прошла под QEMU. Бинарные архивы не добавляются в Git и не являются
публичной release-поставкой.

Wireless использует прежний upstream
`906e9ebb27da8c6a715cd7abab4abfe8a8d29427` и прежний DetMP patch. WFC сохраняет
pin/source/dependencies из [своего recipe](../../../packaging/emulators/melonds-wfc/build.py).
Общий [ARM64 toolchain](../../../packaging/emulators/melonds/arm64-fedora44.cmake)
задаёт также target для ASM: без этого WFC JIT-сборка выбирала x86 assembler.
WFC patch comparison получил явный `--abbrev=7`, чтобы одинаковый diff не
отклонялся из-за разной Git abbreviation на Windows/Linux.

[stage-arm64.py](../../../packaging/emulators/melonds/stage-arm64.py) готовит
Wireless frontend, offline CPython 3.14/aarch64 wheels, исходный upstream archive,
recipe/patch, LICENSE и SHA256SUMS. `install.sh` проверяет архитектуру, Python и
хеши, затем создаёт **новый** каталог runtime. Он не переключает текущую версию
и не касается личного прогресса. Совместимая новая оболочка нужна отдельно.
Пакет WFC содержит core, admission manifest, dependency pins и upstream notices.

Следующий шаг после доступности устройств: включить изменения в свежую общую
production-сборку, проверить зависимости целевого хоста и доставить оба пакета
в новые version directories с сохранением текущих версий и данных. До этого
не объявлять новые возможности установленными. Rollback при закрытой игре:
вернуть предыдущие bundle/shell, оставить backups/recovery/progress без изменений.
